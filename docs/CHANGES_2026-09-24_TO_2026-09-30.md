## 2. Changes that affect every client

### 2.1 Errors

- **Every handled error** has the body `{"code": "...", "detail": "..."}`. Auth errors may add `retry_after_seconds`.
- **Schema errors** (422) now have the same shape, plus `errors[]`:

  ```json
  {"code": "validation_error", "detail": "…", "errors": [{"field": "phone", "loc": ["body","payload","phone"], "message": "Field required", "type": "missing"}]}
  ```

- **`ERROR_CODES.md`** lists all **159 codes** with their HTTP status. It is generated from the source, and a test fails when it is out of date.
  - Translate by `code`; `detail` is English and may change.
  - Codes are stable.
- **`401` without a `code`** means a missing or expired token: refresh once, then log in again.

### 2.2 Other conventions

- **Path ids are UUIDs.** A malformed id returns `422`, never a `500`.
- **GPS values can be sent raw.** The server rounds latitude and longitude to 6 decimal places and accuracy to 2; only impossible values are rejected.
- **CORS** is enabled on `/api/*` for an allowlist of origins, with no credentials mode:
  - `CORS_ALLOWED_ORIGINS` holds the explicit list;
  - `CORS_ALLOW_LOCALHOST` allows any localhost port (test phase only).
- **Lists** in the admin API return `{"count", "items"}` with `limit` and `offset`.

## 3. Authentication and accounts (app)

| Change | Details |
| --- | --- |
| **`OTP_ACCEPT_ANY_CODE` removed** | It let any code open any account. |
| **OTP test numbers** | Listed numbers get a fixed code and no SMS. All test numbers stop on a set date (`OTP_TEST_MODE_UNTIL`). |
| **OTP limits** | Daily limit per phone and hourly limit per IP. Phone numbers are normalised. An SMS provider failure returns `503`, not `500`. |
| **Token refresh and logout** | `POST /api/auth/token/refresh` rotates the pair and blacklists the old refresh token. `POST /api/auth/logout` takes `{refresh, device_token}`. Access tokens last 15 min, refresh tokens 7 days. |
| **Suspended or deleted accounts** | Refused on every request (`401`). |
| **Social login hardening** | An existing account is linked by email only when both the provider and the local account have verified that email. This stops account pre-hijacking. |
| **Admins cannot use the app** | OTP and social login refuse admin accounts (`403 admin_login_required`). |
| **Sign in with Google** | `POST /api/auth/social/google` with `{"token": "<Google ID token>"}`. The server checks the signature, expiry, issuer, and `aud` against `GOOGLE_OAUTH_CLIENT_IDS` (the Web client ID). Errors: `401 social_auth_failed`, or `401 provider_not_configured` for Apple, which is not configured yet. |
| **Delete my account** (App Store / Google Play requirement) | See below. |

**Delete my account:**
- **Confirmation screen:** `GET /api/auth/me/deletion` returns `{can_delete, blockers[]}`. The possible blockers are `active_booking`, `payment_in_progress`, `active_job` and `payout_pending`.
- **Delete:** `POST /api/auth/me/delete` with `{"confirmation": "DELETE"}` returns `204`.
- **What deletion does:**
  - Anonymises the account; it is permanent.
  - Cancels unpaid requests.
  - Takes a cleaner offline and declines their open offers.
  - Ends every session at once.
  - Frees the phone number, so it can sign up again as a new account.
- **What it keeps:** completed bookings, payments and payouts, without the person's identity.
- **Status:** the account becomes `DELETED` and cannot be reactivated.

## 4. Bookings and dispatch

### 4.1 Requesting a cleaner

- **On-demand:** omit `scheduled_at` in `POST /api/bookings`. There is no lead time.
- **Scheduled:** send `scheduled_at`. It must be at least `BOOKING_MIN_LEAD_MINUTES` (120) ahead.
- **Service hours are set in the admin dashboard, and are off by default** (requests accepted at any hour).
  - The fixed 07:00–19:00 rule is **gone**.
  - When enabled, the window is property-local and may run past midnight. On-demand requests and scheduled visits must fall inside it; otherwise `400 outside_business_hours`.
- **`QuoteOut.service_hours`** carries the current rule so the app can block before sending: `timezone`, `enabled`, `opens_at`, `closes_at`, `is_open_now`, `next_open_at`, `min_lead_minutes`.
- **Reschedule** without `scheduled_at` re-requests now.
- **`BookingOut` new fields:**
  - `is_on_demand`, `requested_at`, `cancelled_at`, `cancellation_reason`;
  - `review`, `review_required`, `reclean_eligible_until` (§7);
  - `payment.refunded_amount` (§6.4).

### 4.2 Quotes

- **Bug fixed:** booking with `quote_id` always failed with `404 "Service type … not found"`. It works now.
- **"Up to" amount:** `maximum_total` = services total + `maximum_travel_fee`. The admin sets that fee (§9.6); the default of 9999.99 must be replaced with a real value.

### 4.3 Cancellation

- **Customer:** `POST /api/bookings/{id}/cancel` with an optional `reason`.
- **Admin:** `POST /api/admin/bookings/{id}/cancel` with a required `reason`.
- **When it is allowed:** only while the booking is `PENDING` and nothing is charged. Otherwise:
  - `409 booking_not_cancellable`;
  - `409 cancellation_requires_support`.
- **Effect on the cleaner:** a live or reserved offer closes, and the cleaner receives `offer.cancelled`.

### 4.4 Dispatch

| Rule | Details |
| --- | --- |
| Radius | 50 km. |
| Offers | One live offer per booking at a time. An offer never outlives the visit. |
| Offer responses | Accepting or declining locks the booking and offer rows and requires the booking to still be `PENDING`. |
| Who is excluded | Suspended cleaners, and cleaners without a verified ABN and valid insurance. |
| **Online location feed** (new, required) | The cleaner app sends `PUT /api/contractor/location` with `{latitude, longitude, accuracy, recorded_at}` every 1–2 minutes while available. Dispatch uses only a location from the last 5 minutes. `GET /api/contractor/location` shows `is_fresh`. |
| Distance | Straight-line fallback when no directions provider is configured (test phase). |
| Recovery | Stranded `SEARCHING` bookings are re-dispatched. A repair task completes missing jobs, charges and payouts. |

### 4.5 Offers (cleaner)

- **Endpoints:** `GET /api/contractor/offers` (open offers; `?include_closed=true` adds history) and `GET /api/contractor/offers/{id}`.
- **Frozen at offer time:** `contractor_earnings`, `total_amount`, services, suburb and ETA.
- **`close_reason`** on every offer: `DECLINED`, `TIMED_OUT` or `BOOKING_CANCELLED`, and `null` while open or accepted.
  - A cancelled booking also sets the offer to `EXPIRED`, so read `close_reason` to tell a cancellation from a timeout.
  - On app open, re-fetch any offer the cleaner was waiting on.

## 5. Jobs

### 5.1 Lifecycle

`ASSIGNED` → **`ARRIVED`** (new) → `IN_PROGRESS` → `AWAITING_CUSTOMER_CONFIRMATION` → `COMPLETED`

### 5.2 Arrival

- `POST /api/contractor/jobs/{id}/arrive` with the device's `{latitude, longitude, accuracy}`.
- Accepted within 300 m of the property, plus up to 100 m of reported accuracy; otherwise `409 not_at_property`.
- Sets `arrived_at`, ends live tracking, and notifies the customer (`job.arrived`).
- `/start` now requires `ARRIVED`.
- Arrival and start both require a successful customer payment (`409 payment_not_settled`).

### 5.3 Photos

- Upload only while `IN_PROGRESS`.
- JPEG, PNG, WebP or HEIC, checked by file content.
- 10 MB maximum per photo, 30 photos maximum per job.
- `mark-done` needs at least one `BEFORE` and one `AFTER` photo.
- **Remove a photo** (new): `DELETE /api/contractor/jobs/{job_id}/photos/{photo_id}` returns `204`.
  - Allowed only while `IN_PROGRESS`; `409` after mark-done.
  - The file is also removed from storage.

### 5.4 Customer does not confirm (auto-confirm)

| After mark-done | What happens |
| --- | --- |
| **6 hours** | One reminder push, `job.confirmation_reminder`. |
| **12 hours** | The job is confirmed automatically: `auto_confirmed: true`, payout released, customer receives `job.auto_confirmed`. |

- `JobOut.auto_confirm_at` is the deadline while the job awaits the customer.
- Both steps run in the 5-minute cron.

### 5.5 Photo storage (R2)

- Photos are stored privately in Cloudflare R2 (S3-compatible).
- `signed_url` is a temporary link, valid 1 hour by default. Re-fetch the job for fresh links; do not cache them.
- `503 photo_storage_unavailable` means storage refused the file. Nothing is saved; retry.

## 6. Payments (Stripe)

### 6.1 Flow

The charge happens when a cleaner accepts, possibly while the app is closed, so the card is saved first.

1. **Before the card form:** `POST /api/payments/setup-intent` with `{"stripe_version": "<SDK API version>"}`.
   - It returns `client_secret` (SetupIntent), `setup_intent_reference`, `customer_reference` (`cus_…`) and `ephemeral_key`.
   - Present **PaymentSheet in setup mode**. Google Pay and Apple Pay work inside it.
   - Any 3-D Secure check happens here, while the customer is present.
2. **Create the booking** with the saved `pm_…` as `payment_method_reference`. If it is omitted, the customer's most recently saved card is used.
3. **When a cleaner accepts,** the server charges the saved card off-session. The result is `SUCCEEDED`, `FAILED` (with `failure_reason`) or, rarely, `REQUIRES_ACTION`.
4. **On `REQUIRES_ACTION`** (push `payment.action_required`):
   - `GET /api/bookings/{id}/payment` returns `action_payload: {type, client_secret, payment_method}` to the booking's customer, only while that status lasts.
   - Call `confirmPayment(client_secret)`.
   - Then call `POST /api/bookings/payments/{id}/confirm-action`, which no longer returns `501`.
5. **`POST /api/payments/webhooks/stripe`** (signature-verified) settles pending payments on the server. Keep polling the booking as today.

### 6.2 Details

- **Method:** `payment.method` comes from the card itself: `GOOGLE_PAY`, `APPLE_PAY` or `CARD`.
- **Display name:** `method_summary.display_name` gives, for example, "Visa •••• 4242".
- **Card checks:** a card that belongs to another Stripe customer is refused. A decline at card attach is a normal `FAILED`.
- **Retry:** `POST /api/bookings/payments/{id}/retry` works only for `FAILED` or `REQUIRES_ACTION`, with an optional new `pm_…`.
- **Test cards:**

  | Card | Result |
  | --- | --- |
  | `4242 4242 4242 4242` | Success |
  | `4000 0027 6000 3184` | 3-D Secure |
  | `4000 0000 0000 9995` | Declined |

### 6.3 Money safety

- Provider calls run outside database transactions. An error with an unknown outcome leaves the payment `PROCESSING` for reconciliation; it is never silently marked failed or charged twice.
- Each charge attempt has its own idempotency key.
- **A cleaner is paid only after a successful customer payment.**

### 6.4 Refunds

- **Endpoint:** `POST /api/admin/payments/{id}/refund` with `{amount?, reason}`. Any admin can refund.
- **Full or partial:**

  | Refund | `status` | `refunded_amount` |
  | --- | --- | --- |
  | Full | `REFUNDED` | The whole amount paid. |
  | Partial | stays `SUCCEEDED` | The total refunded so far. |

  Partial refunds add up, never beyond the amount paid.
- **Customer view:**
  - `refunded_amount` and `refunded_at` are on the payment.
  - `refunded_amount` is also on `BookingOut.payment`.
  - The customer receives push `payment.refunded` with the amount. Show the refund message whenever `refunded_amount > 0`.
- **The cleaner's payout is not changed.**

## 7. After the clean

### 7.1 Rating (mandatory)

- `POST /api/bookings/{id}/review` with `{stars: 1–5, comment?}`.
  - Allowed once the job is `COMPLETED`, and only once; it cannot be edited.
  - Errors: `409 review_not_allowed`, `409 already_reviewed`.
- **While a completed booking is unrated, `POST /api/bookings` returns `409 review_required`.** `BookingOut.review_required` marks the booking to rate.
- **Cleaner side:** push `review.received`, and `rating_average` / `rating_count` on the contractor profile.

### 7.2 Re-clean guarantee (72 hours)

- **Eligibility:** the admin marks which services are covered (`ServiceType.reclean_guarantee`). `BookingOut.reclean_eligible_until` is set when the job is completed and a covered service is in the booking.
- **Request:** `POST /api/bookings/{id}/reclean-requests` with `{areas[], details}`. `GET` on the same path returns the history.
  - Areas: `KITCHEN`, `BATHROOMS`, `BEDROOMS`, `LIVING_AREAS`, `WINDOWS`, `OTHER`.
  - Errors: `409 reclean_not_eligible`, `409 reclean_window_closed`, `409 reclean_already_open`.
- **Decision:** the admin approves or rejects the request; the customer receives `reclean.updated`.
- **Limits:** no limit on the number of requests, but one open request at a time. Arranging the visit is manual for now.

### 7.3 Invoice

- `GET /api/bookings/{id}/invoice` (customer) and `GET /api/admin/bookings/{id}/invoice` (admin).
- Available once paid; `409 invoice_not_available` before.
- Contents:
  - Number `INV-YYYY-NNNNNN`, sequential per year and fixed once issued.
  - Lines from the frozen prices (services, then travel, then a rounding line if any).
  - Total and payment details.
  - **No GST** (`gst_included: false`).
- A PDF version is not built yet.

## 9. Admin dashboard

### 9.1 Admin login

1. `POST /api/admin/auth/login` with email or phone plus password.
2. `POST /api/admin/auth/verify` with the SMS code.

**Rules:**
- **Trusted devices:** a trusted device skips the SMS code for 30 days (`device_token`). Manage devices with `GET` and `DELETE /api/admin/auth/devices`.
- **Lockout:** after 5 failed attempts the account is locked for 15 minutes (`429 account_locked`).
- **Temporary passwords:** they force a change. Until the admin changes it, every endpoint returns `403 password_change_required`. Change it with `POST /api/admin/auth/password`.
- **Password policy:** at least 12 characters, not common, not all digits.
- **Other endpoints:** `POST /resend` and `GET /me`.

### 9.2 Admin accounts (superuser only)

- **Endpoint:** `/api/admin/admins`, with list, create, detail, update, `reset-password` and `revoke-sessions`.
- **Temporary passwords:** create and reset each return a temporary password once.
- **Safety rules:**
  - A superuser cannot demote or deactivate themselves.
  - At least one active superuser must remain.
- **Audit:** every action is audited.

### 9.3 Back-office lists and actions

| Area | Endpoints and notes |
| --- | --- |
| Dashboard | `GET /api/admin/dashboard/summary` |
| Users | List with filters, detail, `suspend` (reason required) and `reactivate`. Suspension ends all sessions and takes a cleaner offline. Status `DELETED` = self-deleted; cannot be changed. |
| Properties | List and detail (read-only). |
| Bookings | List (`q` matches the booking reference), full detail (dispatch history with `close_reason`, payment, job, payout), `cancel`. |
| Jobs | List and detail, with photos and `auto_confirmed`. |
| Payments | List and detail, `refund` (any admin), `reconcile` (superuser, for unknown-outcome payments). `needs_reconciliation` filter. |
| Payouts | List and detail, `reconcile` (superuser). |
| Contractors | Verification history per contractor, plus the existing review endpoints. |
| Support | List, detail, status change (`SUBMITTED` → `UNDER_REVIEW` → `RESOLVED`; `RESOLVED` is final). |

### 9.4 Service catalog

- `ServiceType.reclean_guarantee` is new: it puts the service under the 72-hour re-clean guarantee.

### 9.5 Settings screen

**Endpoint:** `GET/PATCH /api/admin/pricing-config`. `PATCH` is partial: send only what changes.

| Field | Meaning |
| --- | --- |
| `price_per_km` | Travel rate per kilometre. |
| `included_distance_km` | Free distance; only the excess is charged. |
| `maximum_travel_fee` | Cap on the travel component. **This is also the customer's "Up to" amount.** |

- **Read-only fields:** `currency`, `pricing_version` (goes up on pricing changes only), `active_from`, `updated_at`.
- **Scope of changes:** they apply to new quotes and offers only. Frozen prices never change.

## 10. Operations (for reference)

- **Hosting:** Railway, running the Procfile `web` line. It applies migrations, collects static files, then starts gunicorn.
- **Health check:** `GET /api/health/ready` returns 200 only when the database answers and no migration is pending.
- **Cron:** a separate Railway service runs `python manage.py run_periodic_tasks` every 5 minutes. Tasks:
  - offer expiry;
  - auto-confirm and reminders;
  - post-confirmation repair;
  - push retry and cleanup.
- **Providers are chosen by environment variables:**

  | Provider | Variable |
  | --- | --- |
  | Payments | `PAYMENT_PROVIDER_ADAPTER_CLASS`, `STRIPE_*` |
  | Storage | `JOB_STORAGE_ADAPTER_CLASS`, `STORAGE_S3_*` |
  | Social login | `SOCIAL_AUTH_ADAPTER`, `GOOGLE_OAUTH_CLIENT_IDS` |
  | Push | `FIREBASE_CREDENTIALS_JSON` |

- **Fake adapters** refuse to run on production unless their switch is on.
- **New timing settings:**
  - `JOB_CONFIRM_REMINDER_HOURS` (6)
  - `JOB_AUTO_CONFIRM_HOURS` (12)
  - `RECLEAN_GUARANTEE_HOURS` (72)
  - `JOB_ARRIVAL_RADIUS_M` (300)
  - `STORAGE_SIGNED_URL_SECONDS` (3600)

## 12. Rules that changed during this period

Read these if you built against an older description.

| Old | Now |
| --- | --- |
| Booking needed `scheduled_at` at least 2 h ahead | Omit it for on-demand; the 2 h lead applies to scheduled bookings only. |
| Fixed 07:00–19:00 hours | No hours by default; the admin sets them (§4.1). |
| `/start` meant arrived and started | `/arrive` first, then `/start`. |
| No cancellation | Free cancellation before payment (§4.3). |
